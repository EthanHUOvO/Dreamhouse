# Dreamhouse 双门户平台 v1

这个版本将整个项目正式拆成两个角色系统，且两端共享同一套订单、Design Version、BOM、设备状态和施工进度数据。

## 入口

```text
/              角色入口
/customer/     住户端
/contractor/   施工方端
```

## 一、住户端

住户只看到三个阶段：

```text
设计 → 施工 → 验收
```

右侧是垂直步骤导航。项目即使已经进入施工，住户仍然可以点击“设计”回看旧方案。

### 设计页

固定为：

```text
对话式交互 | 2D图纸 | 3D Pascal 展示
```

如果项目已经进入施工，设计页不会直接允许覆盖 Approved Design，而是显示“重新设计”。点击后：

```text
Approved V2
→ 新建 Draft V3
→ 在 V3 中修改
→ 提交设计变更
→ 施工方收到 Change Request
→ 施工方接受后 V3 才变成 Approved
```

这解决了“已经施工了，但住户想回到第一步重新设计”的问题。

演示中还内置了一个更自由的改造例子：

```text
把儿童房拆成两个房间，一个书房，一个储物间，把原书房改成儿童房
```

会得到新的 Scene，而不是固定跳到育儿模板。

### 施工页

住户只看结果：

- 整体施工进度
- 设计完成 / 生产完成 / 到场 / 装配 / 验收里程碑
- 现场视频

不会显示 G-code、打印机温度、机器人关节等施工方数据。

### 验收页

显示：

- Approved Pascal 设计模型
- 墙体布局检查
- 门窗位置检查
- 家具与空间功能检查
- 施工完成度
- 确认验收

## 二、施工方端

左侧是多订单管理，预置 4 个独立订单：

```text
DH-2026-001  施工中
DH-2026-002  生产中
DH-2026-003  施工中
DH-2026-004  已完成
```

每点一个订单，右侧全部数据切换到该订单。

支持筛选：

```text
全部 / 生产 / 施工 / 完成
```

右侧单订单详情严格按照白板：

```text
┌────────────────────────┬────────────────────────┐
│          生产           │          施工           │
├────────────────────────┼────────────────────────┤
│ BOM清单及排序展示       │ 人工         机械臂      │
├────────────┬───────────┼────────────────────────┤
│ 墙体        │ 家具      │ 状态信息（机械臂）       │
├────────────┴───────────┼────────────────────────┤
│ 状态信息（3D打印机）    │ 视频                    │
├────────────────────────┤                         │
│ 视频                   │                         │
└────────────────────────┴────────────────────────┘
```

如果住户端提交了设计变更，施工方同一订单顶部会出现：

```text
收到设计变更
V2 → V3
[接受变更]
```

## 数据方式

当前可部署 Demo 为纯前端版本，使用：

```text
localStorage: dreamhouse.dualportal.orders.v3
```

所以同一个域名、同一个浏览器中，住户端与施工方端的数据是联动的。

正式多人部署时，将 `lib/order-store.ts` 换成数据库/API 即可；页面架构不需要重写。

## Pascal

住户设计页和验收页都使用 Pascal Viewer：

- Door / Window 为墙体子节点
- 门窗使用正确的 wall-local distance
- 中间只显示住宅，不显示 Pascal Editor 工具栏
- 移动端自动关闭高负载阴影和边缘效果

## 本地运行

要求 Node.js 22：

```bash
npm install --no-audit --no-fund
npm run check:project
npm run dev
```

打开：

```text
http://localhost:3000/
http://localhost:3000/customer/
http://localhost:3000/contractor/
```

## GitHub Pages

工程支持 `output: 'export'`，并自动处理 GitHub Pages 的 `/Dreamhouse` basePath。

```bash
git add -A
git commit -m "rebuild Dreamhouse as dual portal"
git push origin main
```

然后：

```text
Settings → Pages → Source → GitHub Actions
```

## Vercel / 独立域名

当前静态版本可以直接导入 Vercel 并绑定域名。

如果后续接真正 LLM、真实打印机和机械臂后端，建议：

1. 去掉 `output: 'export'`
2. 将 `order-store.ts` 改为数据库/API
3. 在 Next.js Server/API 中保存 LLM Key 和设备凭据
4. 部署 Vercel / 云服务器 / 内网服务器


另外，所有方案均已删除“客餐厨一体”和走廊之间的那段墙体，客餐厨一体现在直接与走廊连通；其余墙体、门窗和房间逻辑保持不变。


## 本次模型细节修正

根据最新确认的等距俯视图，对基础住宅模型做了生活化细节修正：

- 保留所有门，不再出现“门消失”的问题；
- 调整主卧床朝向，使其更符合卧室开门、窗户与通行关系；
- 调整主卧衣柜位置与朝向，避免与床形成不合理对冲；
- 调整卫生间布置，避免开门后正对或直接撞上淋浴区；
- 卫生间内部改为更合理的进入动线：入口缓冲区 → 马桶 / 台盆 → 淋浴区。


## 进一步家具细调与场景检查

已对各个固定方案继续做了一轮摆放检查和修正，重点包括：

- **基础方案**：主卧床、床头柜、衣柜以及卫生间动线已继续细调；
- **两人共同居住方案**：衣帽间改为更接近真实步入式衣帽间的布置；双人书房两组桌椅重新对齐；
- **育儿家庭方案**：儿童房床位、床头柜、书桌与斗柜重新布局；
- **育儿 + 保姆方案**：保姆房补充更合理的床与床头柜动线；
- **空间重新规划方案**：新书房、储物间以及由原书房改造的儿童房都做了重新摆放；
- **卫生间拆分方案**：主卫增加更合理的淋浴、台盆与马桶关系，公卫保留简洁的台盆 + 马桶布局。


## 本轮细节追加修正

- 主卧衣柜进一步移动到更靠近内墙的位置；
- 避开主卧门侧，避免柜体挤占开门后的通行空间；
- 衣柜朝向改为面向卧室内部；
- 卫生间洗手台继续贴墙摆放，不再竖向立在空间中部；
- 主卫、公卫的洗手台也同步调整为更贴墙的布置方式。
